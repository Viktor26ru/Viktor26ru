## 3. Зачем отдельный контур в Cursor Cloud

Прод-дашборды сами являются частью системы. Если ляжет 214, портал заявок не скажет, что он лёг. Облако Cursor — другой failure domain: другой провайдер, другие ключи, свой SQLite, свои боты.

Ограничение честно: Cloud Agent **не вечный хостинг**. Пока этот агент жив — контур работает. Когда ран уйдёт в archive/expire, процесс умрёт. Поэтому:

1. сейчас поднимаем его здесь и держим агента;
2. `app.py --daemon` + `.cursor/environment.json` поднимают контур на следующем агенте;
3. тот же код можно поставить на cursordev (300G, 32G RAM) как второй независимый сторож — это следующий шаг, не сделан автоматически, чтобы не плодить ещё один systemd без команды.

iOS: Cursor iOS управляет **этим агентом**; Telegram `@Crazynewaibot` — карманный пульт; MAX трёх проектов — тот же командный язык; веб-дашборд на :8787 смотрится с десктопа через port-forward Cursor (на телефоне без публичного ingress его не открыть, поэтому TG/MAX — основной UI в поле).

## 5. Каналы управления

Один маршрутизатор команд (`/status`, `/x5`, `/restart x5 collector`, «что горит», «рестарт коллектора чижик»).

| Канал | Как | Кто |
|---|---|---|
| Telegram `@Crazynewaibot` | long poll из облака | после `/start BIND_CODE` |
| MAX X5 / Чижик / ПМ | poll `/updates` **на самом хосте** по SSH, ответ тем же ботом | allowlist Виктор/Данил |
| Веб :8787 | POST `/api/command` | ключ дашборда |
| Cursor iOS | этот агент читает те же снимки | аккаунт Cursor |

Технические вопросы инфры агент шлёт в Telegram (и дублирует в MAX ПМ Виктору `330798756`).

Restart только allowlist юнитов, `sudo systemctl restart`, cooldown 5 мин, запись в журнал. PostgreSQL автоматически не трогаем. Диск — только алерт.

## 6. Автовосстановление

1. Потоки ops-control (http/collector/telegram) сами поднимаются, если умерли.
2. Прод: 2-й контур `AUTO_HEAL=1` — если core unit не `active`, рестарт + алерт. Успех закрывает инцидент.
3. HTTP 5xx/timeout и диск ≥85% — инцидент, без слепого рестарта postgres.
4. Не чиним бизнес-логику (неверная заявка, SLA) — только процесс и порт.

Первые найденные проблемы, которые контур должен держать на виду:

- диск 214 79% (порог предупреждения 70, авария 85)
- `github-daily-backup` failed, 680MB > 500MB
- Чижик TLS к `platform-api2` без Минцифры
- X5 journal 4G

## 7. Полезные функции сверх «жив/не жив»

Имеет смысл в этой же панели, потому что так ты уже работаешь:

1. **Радар сгорания SLA** (read-only с 214): заявки, у которых portal `slaDate` ближе/прошла, а `resolved_at` пуст. Фотоотчёт не замораживает urgency.
2. **Саморегистрация MAX** — индикатор «закрыта по умолчанию», команда открыть только на названные ФИО и закрыть обратно.
3. **Ростер техников** — жёсткие правила: Пушенко только ФУЛЛ; Latfulin только канонические MAX id.
4. **Префлайт деплоя** — напоминание `deploy_preflight.py` / запрет сырого scp; изоляция окон.
5. **Нагрузка MAX** — 30 rps / 2 msg/s на диалог, last_activity бота, ошибки 429/401.
6. **Токены LLM** — модели с хостов + события, которые проходят через этот контур; полный billing ProxyAPI — когда дадите кабинет/лог.
7. **Утренний дайджест** в TG: диск, failed units, открытые инциденты, сгорающие SLA, backup.
8. **Журнал команд** — кто с TG/MAX сделал restart.
9. **Изоляция проектов** — не дать команде «задеплой на всех».
10. **Бэкап 214** — отдельный инцидент, пока дерево > лимита.

В этом запуске сделаны пункты 5 (MAX `/me`), 6 (модели + учёт событий контура), 8, 9, диск/failed units, команды restart. SLA-радар и замок саморегистрации — следующий слой на тех же пробах (нужен read-only SQL/флаг в config, без записи в прод).

## 8. Безопасность

- Токены MAX и ProxyAPI **не в git**. Пробы MAX идут с хоста.
- Telegram-токен только в `.secrets.env` (gitignore) и store агента.
- SSH-ключи в `~/.ssh` и store, не в репозитории.
- Дашборд за ключом. TG/MAX — allowlist.
- Облако имеет egress без ограничений; входящий HTTP с телефона без port-forward недоступен — это нормально.
- Токен TG уже светился в чате — после привязки лучше перевыпустить в BotFather и прописать в `.secrets.env`.
