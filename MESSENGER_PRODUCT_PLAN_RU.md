# Мобильный мессенджер для iOS и Android: продуктовый и технический план

## 1) Ключевая идея

Сделать безопасный кроссплатформенный мессенджер «как Telegram по удобству», но с **жёсткой приватностью по поиску людей**:

- Без публичной регистрации через email/логин.
- Пользователя **невозможно найти по логину/нику/телефону**.
- Новый контакт появляется только по **одноразовому приглашению** от уже существующего контакта.

## 2) Требования из задачи

- Платформы: Android + iPhone (iOS).
- Онбординг без классической регистрации и без публичного каталога пользователей.
- Поиск контактов — только через приглашения (invite-only graph).
- Обмен:
  - текстовые сообщения;
  - голосовые сообщения;
  - видеосообщения.
- Звонки:
  - голосовые;
  - видеозвонки.
- Безопасность: end-to-end шифрование, защита метаданных, защита от перебора идентификаторов.
- UX: максимально привычный и быстрый интерфейс в стиле топ-мессенджеров.

## 3) Рекомендуемый стек

## Клиент

- **Flutter** (один код для iOS/Android, быстрая итерация, хорошая производительность).
- Локальная БД: SQLite (Drift) + безопасное хранилище ключей в Keychain/Keystore.
- Реалтайм транспорт: WebSocket + fallback на push notifications.
- Медиа и звонки: WebRTC (нативные плагины).

## Сервер

- API + realtime gateway: Go или Rust (высокая нагрузка, низкая задержка).
- Message queue: NATS / Kafka (доставка событий).
- Хранилище:
  - PostgreSQL (аккаунты, устройства, инвайты, служебные метаданные);
  - объектное хранилище (S3-совместимое) для вложений в зашифрованном виде.
- Push: APNs (iOS), FCM (Android).
- TURN/STUN для звонков (coturn).

## Криптография

- Протокол уровня Signal (X3DH + Double Ratchet) для E2E сообщений.
- Для групп — Sender Keys / MLS-подобный подход.
- Подписи устройств: Ed25519, обмен ключами X25519.
- Шифрование файлов: AES-GCM, ключ файла отдельно шифруется на получателя.

## 4) Модель идентичности без поиска

Чтобы «даже зная логин нельзя было найти человека», лучше **вообще убрать глобальный логин**:

1. При первом запуске клиент генерирует:
   - device key pair;
   - user master key;
   - анонимный внутренний `user_id` (непубличный).
2. У пользователя нет публичного username в общем индексе.
3. Добавление контакта только так:
   - пользователь A создаёт одноразовый invite-token (короткоживущий, подписанный сервером, single-use);
   - передаёт его B (QR/ссылка/nearby);
   - B активирует токен, и только тогда между A и B создаётся связь в графе контактов.
4. Сервер не предоставляет endpoint'ов «поиск по имени/телефону/нику».
5. Защита от перебора:
   - токены высокой энтропии;
   - короткий TTL;
   - rate limiting + device attestation + anti-abuse.

## 5) Как сделать «без регистрации» и при этом не потерять аккаунт

Полностью без регистрации возможно, но риск потери доступа высокий. Практичный вариант:

- Базовый режим: вход как анонимный криптографический аккаунт (без email/телефона).
- Опционально: зашифрованный backup-файл (или seed-фраза) для восстановления.
- Дополнительно (по желанию пользователя): привязка recovery-метода (email/телефон) **только для восстановления**, но не для поиска.

## 6) Сообщения и медиа

- Текст: E2E, статусы доставки, редактирование/удаление, цитирование.
- Голосовые:
  - запись в Opus;
  - шифрование на устройстве;
  - wave-preview, ускорение 1.5x/2x.
- Видеосообщения:
  - ограничение длины для UX;
  - адаптивное сжатие;
  - миниатюры локально.

## 7) Голосовые и видеозвонки

- WebRTC P2P где возможно.
- Через TURN в сложных сетях.
- E2E media encryption (SRTP + DTLS, при необходимости insertable streams).
- Функции: mute/camera off, переключение камер, сетевой адаптивный bitrate, reconnect.

## 8) Безопасность (минимум для production)

- E2E по умолчанию для личных и групповых чатов.
- Perfect Forward Secrecy.
- Certificate pinning в мобильном клиенте.
- Защита от MITM при первичном связывании (safety number / QR-verification для параноид-режима).
- Лимитирование метаданных: минимум логов, короткие retention-политики.
- Шифрование данных «на диске» на сервере и клиенте.
- Регулярные security audit + bug bounty.

## 9) UX «как Telegram»

- Быстрый запуск, плавный список чатов, предзагрузка аватаров и последних сообщений.
- Жесты: свайпы, закрепы, архив, реакция emoji.
- Единый стиль iOS/Android с платформенными паттернами.
- Умные уведомления (mute, группировка, предпросмотр с приватным режимом).
- Надёжная оффлайн-очередь отправки.

## 10) Поэтапный план разработки

## Фаза 1 — MVP (10–14 недель)

- Инвайт-механика и граф контактов.
- 1:1 текстовые сообщения E2E.
- Голосовые сообщения.
- Базовые push-уведомления.
- Минимальный профиль без публичного поиска.

## Фаза 2 (6–10 недель)

- Видеосообщения.
- Голосовые и видеозвонки (WebRTC + TURN).
- Группы (малые), отправка файлов, улучшения UX.

## Фаза 3 (8+ недель)

- Масштабирование, observability, антиспам и anti-abuse.
- Многоустройность (multi-device) с безопасной синхронизацией ключей.
- Внешний security audit.

## 11) Команда

Минимально:

- 2 Flutter инженера;
- 2 backend инженера (Go/Rust);
- 1 DevOps/SRE;
- 1 QA automation;
- 1 Product/UX designer;
- part-time security engineer.

## 12) Что важно зафиксировать до старта

1. Уровень анонимности vs удобство восстановления аккаунта.
2. Какие метаданные можно хранить и сколько.
3. Юридические требования по регионам (GDPR и локальные аналоги).
4. Модель монетизации (подписка/enterprise/self-hosted).
