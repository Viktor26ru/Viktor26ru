# Аудит сети и безопасности ресурсов (защитный)

Дата инвентаризации: 2026-08-31.  
Контур: Cloud Agent VM репозитория `Viktor26ru/Viktor26ru` + артефакты invite-only мессенджера.

Это **защитный** отчёт: инвентаризация своей среды и спецификации, без сканирования чужих сетей и без процедур атаки. Полноту «всех уязвимостей интернета» такой обзор не обещает — только то, что видно в этой машине и в этом репозитории.

## 1. Что это за «сеть»

Рабочая среда — изолированный pod Cursor Cloud Agent (Ubuntu 24.04), не домашняя LAN и не production-кластер мессенджера.

- Адрес pod: `172.30.0.2/24`, шлюз `172.30.0.1`, DNS `10.0.0.2`.
- Маршруты в `172.16.0.0/12` и `192.168.0.0/16` идут через шлюз платформы (типичная overlay/VPC-схема).
- `docker0` (`172.17.0.1/16`) есть, **dockerd в этом сеансе не запущен**, сокета `/var/run/docker.sock` нет.
- Исходящий трафик среды: **не ограничен** (`egress.restricted = false`).
- Конфиг окружения — personal/DB-managed, в репозитории нет `.cursor/environment.json`.
- Production backend и мобильный клиент в репозитории **отсутствуют**. Есть спецификация, SQL-миграции и локальный Python/SQLite прототип.

Итог: «сеть, в которой мы работаем» = управляемый Cloud Agent + будущий контур продукта. Угрозы разные, ниже разделены.

**Что уже приемлемо в этом pod**

- VNC привязан к localhost.
- В репозитории нет `.env` с секретами; `.gitignore` уже игнорирует `.env` и `*.sqlite3`.

### 3.2 Спецификация API / протокол (ещё не реализовано)

| ID | Критичность | Находка | Как чинить |
|---|---|---|---|
| SPEC-01 | Высокая | `POST /auth/bootstrap` без аттестации устройства | Анонимный bootstrap = фабрика ботов и расход prekey. Нужны device attestation (App Attest / Play Integrity), rate limit по IP/ASN, proof-of-work или invite-to-onboard |
| SPEC-02 | Высокая | Refresh без ротации и без таблицы сессий | Refresh token rotation + reuse detection + отзыв устройства. Хранить только hash refresh. Короткий access (минуты), refresh в secure storage |
| SPEC-03 | Высокая | OpenAPI: Bearer JWT, но нет issuer/audience, JWKS, TTL, revocation | Предпочтительнее opaque access + server-side session. Если JWT — короткий TTL, `aud`/`iss`, deny-list при logout |
| SPEC-04 | Высокая | Нет авторизации на уровне чата/медиа/звонка в контракте | Каждое чтение/запись: membership check. Presigned URL — только владельцу/участнику, TTL секунды, method-lock, content-length |
| SPEC-05 | Высокая | WebSocket `wss://.../v1/ws` без схемы аутентификации | Токен только в первый кадр или cookie, не в query string. Переавторизация при refresh. Origin allowlist |
| SPEC-06 | Высокая | Звонки: SDP/ICE без привязки к контакту и без E2E identity | Сигналинг только между контактами. DTLS + identity binding (или insertable streams). Свой TURN с auth, не открытый relay |
| SPEC-07 | Средняя | `POST /invites/redeem` в OpenAPI без bearer (security: не снят явно, но bootstrap-подобная дыра если redeem публичный) | Redeem только аутентифицированным устройством. Иначе токен + чужой prekey = захват сессии |
| SPEC-08 | Средняя | Протокол просит HMAC/EdDSA и Argon2id; прототип/схема — только hash | В production: подпись `nonce\|\|exp\|\|policy`, на сервере Argon2id (не быстрый SHA-256) + pepper. Ротация ключей подписи |
| SPEC-09 | Средняя | Нет таблицы refresh/sessions, нет unique на `device_pub_key` | Уникальность ключа устройства. Сессии с `revoked_at`. Не хранить push_token без шифрования на диске |
| SPEC-10 | Средняя | `audit_security_events.event_meta` JSONB легко залогирует сырой токен | Схема allowlist полей. Запрет писать token/ciphertext/prekey в аудит |
| SPEC-11 | Средняя | Soft-delete сообщения оставляет ciphertext | Ок для E2E, но нужна политика retention и возможность tombstone без тела. Клиент: удаление ключей |
| SPEC-12 | Средняя | Медиа: `sha256` без уточнения «хэш ciphertext» | Считать hash только ciphertext. Сервер не видит plaintext. Запретить публичный ACL |
| SPEC-13 | Низкая | Нет CORS/CSP/pinning в контракте | Мобильный клиент: certificate pinning. Если появится web — строгий CORS, никаких `*` |
| SPEC-14 | Низкая | Нет модели угроз метаданных (кто с кем, когда, размер) | Минимизировать логи, короткие retention, padding/cover traffic — отдельно решить до launch |

### 3.3 Криптография (план vs дыры)

План (Signal/X3DH + Double Ratchet, Ed25519, X25519, AES-GCM) — правильное направление. Не закрыто:

- Safety number / QR verification при первом контакте (SPEC в product plan есть, в API нет).
- Multi-device sync ключей отложен на фазу 3 — до этого второй девайс = дыра или потеря.
- Backup seed: если появится — только клиентское шифрование, сервер не видит фразу.
- Prekey exhaustion: исчерпание one-time prekeys не должно откатываться на reused key без сигнала пользователю.

## 4. Как сделать «свою сеть и ресурсы» безопасными

Разделено: этот Cloud Agent, будущий backend, ваши собственные серверы.

### 4.1 Cursor / агент (сделать сразу)

1. Включить **egress allowlist** в personal environment (ссылка в ENV-01).
2. Не класть в чат агента пароли порталов, `.pem`, cookie, dump `ps`/`env`.
3. Считать транскрипт агента секретом; не делать репозиторий публичным, если в истории светились токены.
4. GitHub: fine-scoped token, короткий TTL; после подозрительного транскрипта — revoke.
5. Не поднимать в этом pod Postgres с publish на `0.0.0.0`. Compose теперь биндится на localhost.

### 4.2 Локальная разработка мессенджера

1. `make pg-up` только на loopback (уже в compose).
2. Свои пароли в `.env` (файл в gitignore). Пример: `.env.example`.
3. Не коммитить SQLite с прод-данными.
4. `make validate` и `make prototype-test` перед merge.

### 4.3 Когда появится настоящий backend

1. TLS 1.2+ везде, HSTS, отдельный WAF/rate limit на `/auth/*` и `/invites/*`.
2. Сеть: API в private subnet, Postgres без public IP, object storage private endpoint.
3. Postgres: свой role на приложение (без BYPASSRLS/superuser), `sslmode=verify-full`, шифрование диска, backups с отдельным ключом.
4. Secrets: менеджер секретов, не env в git и не `environment:` с паролем в compose на проде.
5. Observability без PII/токенов; алерт на всплеск `INVITE_NOT_FOUND` / failed refresh.
6. Внешний security review до публичного launch (это уже в product plan, фаза 3).

### 4.4 Ваши собственные Linux-хосты (если деплой не в Cursor)

1. Файрвол default deny; SSH только по ключу, нестандартный порт не считать защитой.
2. Автообновления security patch; отдельный unprivileged user для приложения.
3. Docker: никакого TCP 2375; пользователь не в группе `docker`, если не нужно.
4. Fail2ban/crowdsec по SSH; 2FA на GitHub и хостинг-панели.
5. Бэкапы вне той же машины; проверка восстановления.

## 5. Что исправлено в репозитории этим PR

- Postgres в `docker-compose.yml` слушает только `127.0.0.1`.
- Пароль/пользователь БД читаются из переменных окружения.
- Прототип хранит `token_hash`, не сырой token.
- Прототип запрещает чат и сообщение вне графа контактов / членства.
- Демо не печатает полный invite token.
- Добавлен `.env.example`.

## 6. Ограничения этого аудита

- Не выполнялся offensive scan внешних адресов и не писались эксплойты.
- Платформенные порты Cursor (26053–26058, 26500, 50052, 2375) описаны как поверхность; закрыть их должен провайдер среды, не приложение.
- Выводов о домашней/офисной сети заказчика нет: до неё из этого pod доступа нет.
- «Все уязвимости» закрыть одним проходом нельзя: нужен повторный аудит, когда появится HTTP-сервер и клиент.
